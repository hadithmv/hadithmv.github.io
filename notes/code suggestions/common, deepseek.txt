Security (the highest-value ones first)

Audit all code paths where CSV data or URL parameters flow into innerHTML or template strings. The data is user-curated but the app renders it — show me every place a value from a CSV field or from the ?q=/?book=&row= URL params reaches the DOM, and determine whether any of them could inject HTML/JS. Quote each sink with file:line and give a concrete payload if one exists.

Check the CSV/XLSX export code (export.js, export-epub.js) for spreadsheet formula injection:
CSV cells starting with =, +, -, @ that Excel would evaluate. Also check whether the Dhivehi
CSV export writes a UTF-8 BOM (Excel misreads Thaana without it).

Is there anything in the CSV pipeline (registry → book files → search index) that trusts a hash
or version field without verifying it? Trace what happens when data/bookRegistry.csv and the
search index meta.version disagree — is there a degraded-but-safe path or a silent wrong result?

Performance (this is your real bottleneck)

The search index is ~41.6 MB of JSON. Walk the load path: when does it download, when does it
parse, what happens on a low-memory phone? Identify the worst-case memory spike (JSON.parse of
41 MB) and propose the cheapest realistic improvement — don't redesign, just tell me the
highest-ratio fix (streaming parse? moving meta out of the index? splitting by book?).

Find every place a cache is written that could silently never store — keys that don't match
their read path, early returns before the write, async races. (We already found one: a peek
cache wrote with an undefined key so it never cached.) Grep the whole js/ tree for cache
write/read pairs and check each one matches.

The reader fetches and parses whole book CSVs. Which books are the largest, and what does a
cold open of the biggest book cost in bytes + parse time on a mid-range phone? Is there any
part of or way a book CSV or data stuff could be loaded better or lazily or streamed or in parts etc?

Correctness under RTL / bidi (you've hit real bugs here)

Audit every element that mixes Arabic, Thaana, and Latin in one line (book titles, search
snippets, metadata rows) for bidi hazards: what happens when an English word is wrapped in
RTL punctuation, or when a number sits between two RTL words? Give concrete strings that would
render scrambled and where the fix would go (dir attributes, Unicode controls, or CSS).

The scroll wrappers rely on justify-content: safe center and 2px inline-start insets to keep
overflowed content reachable in RTL. Find any OTHER centered container with internal overflow
that wasn't covered — including elements that become overflow containers only on mobile or
only when text is long (pageTitle, search dropdowns, tag rows).

How to make AI audits not lie to you

The single biggest failure mode: an AI reads a few files and confidently asserts "no XSS / no dead code / all caches match". Three rules that fix it:

Demand file:line evidence — every claim must be a quoted line, and forbid "looks fine" as an answer.
Make it falsify, not confirm — "find the sink" outperforms "is this secure?"; "prove this is unreachable" outperforms "is there dead code?".
Give it the failure class you already know about — the peek-cache bug, the wrongly-deleted CSS classes, the stale README numbers. AIs generalize from one example much better than from zero, and each pass teaches them the kind of bug this codebase grows.
